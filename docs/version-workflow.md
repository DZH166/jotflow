# JotFlow 版本迭代规则

这套规则用于让“小董随心录”以后每一次功能完善都能被追踪、验证和恢复，同时保持流程足够轻量。

## 分支

- `main` 始终保存已经完成基本验证的状态。
- 小型文档修订或明确的单点修复可以直接形成一个独立提交。
- 较大功能从最新 `main` 创建 `codex/<version>-<topic>` 分支，例如 `codex/v0.2-sync-safety`。
- 开发分支完成测试和审查后再合并回 `main`，不在失败状态下合并。

## 提交

一次提交只表达一类变化，常用前缀：

- `feat:` 新功能
- `fix:` 缺陷修复
- `test:` 测试与测试基础
- `docs:` 文档
- `refactor:` 不改变行为的结构调整
- `chore:` 工程、依赖或仓库配置

提交前至少运行：

```bash
pnpm test
pnpm build
git diff --check
```

暂存时优先指定文件并检查 `git diff --cached`，避免把 `.env.local`、临时文件或其他未完成任务混入提交。

## 推送与合并

1. 从远程获取最新状态，确认本地分支没有意外分叉。
2. 推送当前开发分支，让 GitHub Actions 完成测试和构建。
3. 检查代码差异和验收结果。
4. 验证通过后合并到 `main`。
5. 再次确认 `main` 的 GitHub Actions 通过。

不使用强制推送覆盖 `main`。出现冲突时先理解双方改动，再进行显式合并。

## 版本标签

项目使用 `vMAJOR.MINOR.PATCH`：

- `MAJOR`：不兼容的数据或产品结构变化。
- `MINOR`：一组可对外描述的新能力，例如 `v0.2.0` 稳定核心。
- `PATCH`：不改变主要能力的小型修复，例如 `v0.2.1`。

只有在对应清单验收完成、`main` 测试与构建通过后才创建版本标签。标签指向已经验证的 `main` 提交，并与 `package.json` 版本保持一致。

## 当前路线

- `v0.1.0`：本地捕捉、离线快照、真实账号和 Supabase 同步纵向闭环。
- `v0.2.0`：账号隔离、同步可靠性、备份安全、密码恢复和手机端账号入口。
- `v0.3.0`：PWA、Android 分享入口、扩展直存和真正模糊搜索。
- `v1.0.0`：完成产品化验收后的首个稳定公开版本。
